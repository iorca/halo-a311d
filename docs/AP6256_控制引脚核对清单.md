### ✅ 真机 pinctrl 检查（差点误判，主动撤回）
```
/sys/kernel/debug/pinctrl/pinctrl-handles:
  device: ffe03000.mmc  current state: clk-gate
```

`pinmux-pins` 里 GPIOX_0/1/2/3/5 显示 `MUX UNCLAIMED`、只有 GPIOX_4 被占——
我一度以为找到「pinmux 没配」的根因，核对 `pinctrl-maps` / `pinctrl-handles` 后确认：
**default state 六组全对，UNCLAIMED 是初始化失败后驱动切到 `clk-gate` 释放 mux 的结果，
不是原因**（和之前 `gpio-71 out lo` 同属「失败后的状态」）。配置正确，排除。

### 剩余候选（按优先级）
1. **IO 电压域**：图上标 `I/O=1V8 or 3V3`。底板 AP6256 VDDIO = 1.8V
   （R146=0Ω → VDDIO_AO18），CMD 上拉 R144 也在 1.8V 域；dts 声明
   `vqmmc-supply=<&vddao_1v8>`。需确认**核心板 SDIO bank 实际供的是 1.8V 还是 3.3V**。
   若 SoC 侧 3.3V、模块侧 1.8V，CMD5 的响应回不到 SoC → 完全静默，与现象吻合。
2. **上电时序（唯一逻辑上能解释「CMD 完全无应答」的软件候选）**：
   `sdio_pwrseq` 没有 `post-power-on-delay-ms`，WL_REG_ON 拉高后立刻发 CMD5，
   模块 PMU 若未稳定就不应答。**推荐实验**（本地改 dtb，2 分钟出结果）：
   `fdtput -t x <dtb> /sdio-pwrseq post-power-on-delay-ms 50` → 重启看 `mmc2`。
3. `max-frequency` 100M→25M：**不推荐先试**。CMD5 走 identification mode（≤400kHz），
   与 `max-frequency` 无关，降频解释不了 CMD 无应答。
4. WL_REG_ON 初始化瞬间波形 / 模块本身（虚焊、损坏）——需示波器或硬件排查。

⚠ 已两次把「失败后的状态」误当成原因、一次把官方电路当缺陷。下结论前先分清因果。

### 21:50 主人补焊 + SDIO bank=1.8V 确认后的实测（三次实验全负）
主人确认核心板 SDIO bank 实际 1.8V（电压域匹配）、并已对模块补焊。重扫后仍 `error -84`。
随后用本地改 dtb 逐个试了软件候选，**全部无效**：

| 实验 | 做法 | 属性确实生效 | 结果 |
|---|---|---|---|
| 补焊后重扫 | unbind/bind `ffe03000.mmc` | — | `error -84` 复现 |
| 上电延时 | `fdtput -t x <dtb> /sdio-pwrseq post-power-on-delay-ms 50`（v6.18 `pwrseq_simple.c:159` 支持） | `/proc/device-tree` 读回 50 | `error -84` 不变 |
| SDIO 内部上拉 | `sdio_pins` 的 `bias-disable` → `bias-pull-up`（上游 `g12-common.dtsi:944` 原本 disable；SD 卡 `sdcard_c_pins` 是 pull-up） | `pinctrl-handles` 的 `CONFIGS_GROUP` 由 `00000001` → `00000105`，与 SD 卡一致 | `error -84` 不变 |

→ **软件侧可改项已穷尽**。补焊、电压域、上电时序、内部上拉四条全部排除。
→ `fdtput -d <dtb> <node> <prop>` 删属性；`fdtput <dtb> <node> <prop>` 不带值可创建
  零长度 boolean 属性（用来加 `bias-pull-up`）——这套手法验证可用。
→ 已把板上 dtb **回退成只含 `shutdown-gpios`**（删 delay、恢复 `bias-disable`），
  与源码 dts 一致；`fdtget` 回读 `2a 3e 0` 确认 BT 修复仍在。

### 剩下的只能靠硬件量测（软件侧无法再推进）
1. **U40.12 (WL_REG_ON / GPIOX_6)**：上电后是否真为高？debugfs 的 `gpio-71 out lo`

2. **CMD 线**（U40.16 / CN3.48 / GPIOX_5）与 **CLK 线**（U40.17 / CN3.50 / GPIOX_4）：

## H. 本轮 dts 改动记录（本地，未 commit / 未 push）

文件：`dt/meson-halo-a311d.dts:995-1011`、`dt/meson-halo-a311d-pcie.dts:962-978`

```dts
/* AP6256 蓝牙：BT_REG_ON(U40.34) 经 R147(47k→GND) + R145(33k)
 * 由 GPIOA_13(CN2-58 / BT_EN_3V3) 驱动：3.3 × 47/(33+47) ≈ 1.94V。
 * ⚠ 不写 shutdown-gpios 时 GPIOA_13 被 47k 下拉，BT_REG_ON = 0 …
 */
bluetooth {
    compatible = "brcm,bcm43438-bt";
    max-speed = <2000000>;
    clocks = <&wifi32k>;
    clock-names = "lpo";
    shutdown-gpios = <&gpio GPIOA_13 GPIO_ACTIVE_HIGH>;   /* 新增 */
};
```

**极性依据**：v6.18 `drivers/bluetooth/hci_bcm.c:1114`
`devm_gpiod_get_optional(dev, "shutdown", GPIOD_OUT_LOW)`，
`:1050-1062` `bcm_gpio_set_shutdown(dev, powered)` → `gpiod_set_value(shutdown, powered)`，
powered=1 即逻辑 1 = active → 用 `GPIO_ACTIVE_HIGH` 才是物理高 = BT_REG_ON 有效。
`GPIOA_13 = 62`（v6.18 `meson-g12a-gpio.h:90`），真机 debugfs gpio 中 gpio-62 未被其它驱动占用。

**本地校验**：`check-variant-diff.py` RC=0（差异 7 行全在白名单）；
两文件 braces 60/60、注释成对；两个变体都写入了 `shutdown-gpios`。
⚠ 当前工作分支 `gxlimg-full-mainline-uboot`；**源码改动只在工作区，未 commit、未同步 main、未 push**。

### ✅ 真机验证（21:20，本地替换 dtb，**没有编译镜像**）

```bash

  /soc/bus@ffd00000/serial@24000/bluetooth shutdown-gpios 0x2a 0x3e 0x00
#   0x2a = &gpio phandle, 0x3e = 62 = GPIOA_13, 0x00 = GPIO_ACTIVE_HIGH
```
